# Stage 01 — критерии приёмки

## Включено в этап

- PostgreSQL миграции с SHA-256 проверкой и блокировкой параллельных запусков.
- Локально создаваемая учетная запись администратора, пароль хэшируется через scrypt.
- Cookie-сессия `HttpOnly`, `SameSite=Strict` с 8-часовым сроком действия.
- Простой RBAC: admin (изменение + публикация), editor (черновики), viewer (только чтение).
- Редактирование начальной страницы с автосохранением через debounce 800 мс.
- Оптимистические ревизии, HTTP 409 при конфликте.
- Публичное API отдаёт опубликованную версию, не черновик.
- Документированы будущие настройки локальной сети, установка на сервер в этом этапе **не проводилась**.

## Что не заявляется готовым

Автозагрузка афиш, Excel, конструктор блоков, WebSocket, multi-kiosk, офлайн-режим, TLS/реверс-прокси, автообновления Windows-службы и продакшн-развёртывание — последующие этапы.

## Лабораторные команды

```powershell
npm install --no-audit --no-fund
npm run check
```

## Ручная приёмка

1. Сначала PostgreSQL 18 с отдельной БД и ролью navikultura (в тестовой среде), затем `npm run migrate -w @navikultura/api`.
2. Задать `DATABASE_URL` и `EDITOR_ORIGIN=http://127.0.0.1:5173` в окружении процесса, не в GitHub.
3. Создать первого admin через команду bootstrap (пароль вводится из безопасного источника stdin, а не в командной строке). При необходимости создать editor/viewer через `create:user`.
4. Запустить отдельно API и web. Проверить вход, ошибку пароля, сохранение и публикацию.
5. Открыть две вкладки редактора, убедиться, что устаревшая ревизия возвращает конфликт, не стирает данные.
6. Проверить что анонимный пользователь и viewer не меняют данные.
7. Сделать резервное копирование `pg_dump` и тестовое восстановление в отдельную БД перед продакшн-внедрением.

**Не устанавливать сервис на DESKTOP-OBLAKO до положительной приёмки и резервной копии.**
